# ДЗ № 4 — Apache ZooKeeper: отказоустойчивый координатор

Это продолжение ДЗ № 3 (вариант № 11 — DevOps-инженер).

## Архитектура

- 3 узла ZooKeeper 3.9.6 / Java 17 в Docker: `lab4-zk1..3`, порты `127.0.0.1:2181..2183`.
- 2 процесса координатора `lab4-coordinator-a` и `lab4-coordinator-b`.
- Выбор лидера через эфемерно-последовательные znodes `/lab4/runs/<id>/election/candidate-*`.
- Сессия 10 с, эпоха лидерства в `.../epoch` с compare-and-set.
- Реальный MapReduce пар из 5 158 вакансий, 21 чанк по 250 строк (последний 158).
- Чекпоинт `results/<id>/checkpoint.json`: индекс следующего чанка + **все промежуточные частоты пар**. Запись атомарная, защищена файловой блокировкой и не допускает регресса по индексу.
- Для независимой сверки берётся `../results/mapreduce/skills_2.csv`; вход — `../results/optimized/devops_skills.csv` из ДЗ № 3. Оба файла примонтированы в контейнеры **только для чтения**.
- Ожидаемо: **22 311 уникальных пар, 134 786 вхождений и полное совпадение по всем парам**.

## Проверки

В PowerShell:

```powershell
cd C:\rustfs-lab\devops-hw\lab4
docker compose up -d zk1 zk2 zk3
docker compose ps
..\.venv\Scripts\python.exe .\offline_reference_test.py
docker compose --profile workers build worker-a
..\.venv\Scripts\python.exe .\quorum_tests.py
```

`quorum_tests.py` по очереди останавливает одного и двух **только ZooKeeper-узлов**, проверяет клиентские операции и **в любом случае пытается восстановить все три**. Сохраняет `evidence/ensemble/quorum.json`, `evidence/ensemble/ephemeral.txt`.

Затем, **только после возврата работоспособности трёх узлов**:

```powershell
..\.venv\Scripts\python.exe .\experiment.py no-fencing
..\.venv\Scripts\python.exe .\experiment.py fencing
```

Каждый эксперимент создаёт новый уникальный путь в ZooKeeper и собственный каталог `logs/<id>`, `results/<id>`, `evidence/<id>`. Он запускает A, затем B, ждёт пяти чекпоинтов, делает `docker pause lab4-coordinator-a`, измеряет переход роли, удерживает процесс приостановленным ~40 секунд, делает `docker unpause` и сверяет конечный указатель. При ошибке в конце всегда предпринимается попытка `unpause`.

Ожидается:
- **FENCING=0:** две строки `PUBLISHED_RESULT`, версия указателя 2;
- **FENCING=1:** публикация B, строка `BadVersionError` от устаревшего A, версия указателя 1, `owner=b`.
- В обоих режимах A и B выполняют полный расчёт и сверяют все частоты с ДЗ № 3; B начинает с сохранённого чекпоинта.
- Время failover и состояние указателя сохраняются в `evidence/<id>/summary.json`.

Важно: намеренно разрешённая запись A без fencing воспроизводит **ошибку приложения** — stale writer. Защищённый указатель хранится непосредственно в ZooKeeper и его запись производится с проверкой версии (`zk.set(..., version=...)`); это даёт **настоящий** `BadVersionError`. Если конечным получателем будет RustFS или БД, этот же принцип ограничения по эпохе должен применяться на стороне **этого получателя**: ZooKeeper не перехватывает чужие операции записи.

## Ответы на вопросы

**Почему 3, а не 2 или 4?** Для согласованной записи нужен кворум большинства. При 2 серверах нужны оба (1 отказ не выдерживается); при 3 нужны 2 (1 отказ выдерживается); при 4 нужны 3 (всё ещё только 1 отказ). Три — минимальное экономичное число для отказоустойчивости к одному узлу.

**Почему эпоху проверяет получатель записи?** После потери ZooKeeper-сессии старый процесс не исчезает: он может выйти из паузы и попытаться записать данные в RustFS/БД. ZooKeeper регулирует свои znode и сессии, но не проверяет все сторонние хранилища. Поэтому хранилище-получатель должно атомарно отклонять токены старых эпох. В лабораторной сам указатель живёт в ZooKeeper; его CAS-проверка служит моделью такого приёмника и вызывает `BadVersionError`.

## Безопасность

- Не останавливать RustFS для экспериментов.
- Все контейнеры ZooKeeper и координаторов имеют префикс `lab4-`.
- Исходные эталоны ДЗ № 3 примонтированы read-only.
- Не удалять Docker named volumes без явного намерения сбросить ансамбль.
- Не включать сырые ключи доступа, учётные данные и пользовательские данные в публичные журналы.
